## 1. 문제: 엑셀 필터로는 걸 수 없는 조건

후보를 찾던 담당자들의 조건은 두 종류가 섞여 있었다.

|조건 종류|예|기존 방식|
|---|---|---|
|정형 조건|마케팅 부서, 과장급 이상, 경력 5년 이상|엑셀 필터로 가능|
|정성 조건|책임감 있는, 전략적인, 고객 관계를 잘 만드는|**필터로 표현 불가**. 평가 텍스트를 사람이 읽고 판단|

정성 조건의 근거는 이미 데이터에 있었다. 수년치 평가·경력 서술 텍스트다. 문제는 그걸 사람이 다 읽을 수 없다는 것이었다. 그래서 목표를 이렇게 잡았다.

- 정형 조건은 **필터**로, 정성 조건은 **텍스트 유사도**로 처리한다.
- 사용자는 자연어 한 줄만 쓴다. 어디까지가 필터이고 어디부터가 유사도 검색인지는 시스템이 나눈다.

## 2. 검색 흐름

```
"마케팅팀에 있는 과장 이상, 재무 3년 이상 근무했던, 신규 서비스 런칭 성공 경험"
        │
        ▼
 ① 질의를 세 갈래로 분류 (파인튜닝한 GPT-4o-mini)
        │
        ├─ filter       "마케팅팀에 있는 과장 이상"     현재 상태
        ├─ job_history  "재무 3년 이상 근무했던"        과거 이력 + 기간
        └─ experience   "신규 서비스 런칭 성공 경험"      서술 텍스트에서 찾을 것
        │
        ▼
 ② 갈래마다 다른 방식으로 사람을 거름
        │  filter       → Text2SQL로 WHERE 절 생성 → 프로필 뷰 조회      (4.2)
        │  job_history  → {키워드, 기간 하한·상한} 추출 → 이력 조회 함수  (4.3)
        ▼
 ③ 두 결과(사번 집합)의 교집합 = 후보군
        ▼
 ④ experience → 키워드 추출 → 임베딩 → 후보군 안에서만 유사도 검색  (3절)
        │  사람마다 가장 비슷한 문서 1건, 유사도 0.75 이상
        ▼
 ⑤ 문서마다 질의와 관련된 근거 문장을 LLM으로 다시 뽑아 함께 반환  (4.5)
```

위 흐름에서 중요한 건 **②·③이 ④보다 먼저**라는 점이다. 정형 조건까지 벡터 유사도에 맡기면 "과장급"과 "대리급"이 의미상 가깝다고 섞여 나온다. 정형 조건은 SQL로 정확히 거르고, 남은 후보 안에서만 뉘앙스를 비교한다. 각 갈래는 질의에 없으면 건너뛰고, 어느 단계에서든 결과가 0명이면 거기서 빈 결과를 돌려준다.

## 3. 하이브리드 서치

### 3.1 왜 하이브리드인가

PoC에서 같은 질의로 세 방식을 비교했다.

|방식|잘하는 것|못하는 것|
|---|---|---|
|Dense만|"전략적인 사람" → "기획·분석 역량이 뛰어남"처럼 표현이 달라도 의미로 찾음|꼭 들어가야 하는 단어("마케팅", 특정 업무명)를 놓치기도 함|
|Sparse(BM25)만|특정 단어가 실제로 있는 문서를 정확히 찾음|동의어, 다른 표현, 오탈자에 약함|
|**하이브리드**|둘의 약점을 서로 보완|가중치 α를 정해야 함|

```
최종 점수 = α × Dense 유사도 + (1 − α) × Sparse 유사도
```

### 3.2 α 정하기

α는 고정값이 아니라 튜닝 대상이었다. "이 질의라면 이런 사람이 나와야 한다"는 사례를 모아 두고, α를 바꿔 가며 상위 결과에 기대 후보가 얼마나 들어오는지 비교했다.

|α 쪽으로 기울면|결과 경향|
|---|---|
|1에 가까움 (Dense 중심)|표현이 달라도 잘 찾지만, 질의의 핵심 단어가 없는 문서도 상위에 옴|
|0에 가까움 (BM25 중심)|단어가 정확히 맞는 문서만 상위. 평가 텍스트가 짧거나 표현이 다르면 놓침|

α를 조절하면 결과를 의미 검색 쪽으로 기울일지 키워드 검색 쪽으로 기울일지 정할 수 있다.

### 3.3 Dense: 임베딩

평가·경력 서술 텍스트를 OpenAI `text-embedding-ada-002`(1536차원)로 임베딩했다. 문서 쪽 임베딩은 [1편](/spark/spark-etl-emr-serverless/)의 배치에서 미리 만들어 두고, 질의 시점에는 질의 하나만 임베딩한다.

### 3.4 Sparse: 한국어 BM25에는 형태소 분석이 먼저

BM25는 단어가 문서에 몇 번 나오는지로 점수를 매긴다. 한국어를 띄어쓰기로 자르면 "책임감이", "책임감을", "책임감은"이 서로 다른 단어가 되어 점수가 흩어진다. Kiwi로 형태소를 분석해 의미 있는 품사만 남겼다.

```python
from kiwipiepy import Kiwi

kiwi = Kiwi()
KEEP = {"NNG", "NNP", "VV", "VA", "XR", "SL"}   # 일반·고유명사, 동사, 형용사, 어근, 외국어

def tokenize(text: str) -> list[str]:
    return [t.form for t in kiwi.tokenize(text) if t.tag in KEEP]

tokenize("고객 관계를 주도적으로 관리하며 책임감이 강함")
# ['고객', '관계', '주도', '관리', '책임감', '강']
```

이 토큰 목록으로 BM25 인코더를 학습(문서 집합의 단어 빈도·문서 빈도 계산)하고, 문서와 질의를 각각 Sparse 벡터로 바꿨다. 조사·어미를 버리니 "책임감이 강하다"와 "강한 책임감"이 같은 토큰으로 모인다.

### 3.5 pgvector에서 한 번에 계산

Dense와 Sparse를 한 테이블에 두고, 유사도 계산은 **DB 함수** 하나로 묶었다. Dense는 pgvector `vector(1536)` 컬럼, Sparse는 [1편](/spark/spark-etl-emr-serverless/)의 배치가 만든 `{"토큰 인덱스": 가중치}` 형태의 JSON(`jsonb`) 컬럼이다. 함수는 Dense 유사도와 Sparse 유사도를 α로 섞은 점수를 돌려준다.

```sql
-- API가 실행하는 쿼리. :q_dense, :q_sparse 는 질의 벡터, :alpha 는 가중치
WITH ranked AS (
    SELECT empno, doc_text, similarity,
           ROW_NUMBER() OVER (PARTITION BY empno ORDER BY similarity DESC) AS rn
    FROM hybrid_similarity_search(
        CAST(:q_dense  AS vector),
        CAST(:q_sparse AS jsonb),
        CAST(:alpha    AS double precision),
        CAST(:success  AS varchar)          -- '성공경험'이면 성공 사례 문서만
    )
)
SELECT empno, doc_text, similarity
FROM ranked
WHERE rn = 1                -- 한 사람의 여러 문서 중 가장 비슷한 1건만
  AND similarity >= 0.7
ORDER BY similarity DESC
LIMIT 20;
```

|결정|이유|
|---|---|
|점수 계산을 DB 함수로|API는 질의 벡터와 조건만 넘긴다. 검색 로직을 바꿀 때 API 배포 없이 함수 버전만 올리면 된다|
|`ROW_NUMBER() ... rn = 1`|한 사람에게 평가 문서가 여러 건이라, 그대로 두면 같은 사람이 상위를 도배한다|
|유사도 하한선|"상위 N명"만 자르면 아무 관련 없는 사람도 N명을 채운다. 하한선 아래는 결과에서 뺐다|
|`성공경험` 플래그|질의에 "성공"이 들어가면 성공 사례로 표시된 문서만 대상으로 했다(4.4)|

### 3.6 운영에서는 Dense만 남겼다

하이브리드 함수는 버전을 올려 가며 튜닝했지만, 운영 API에 올린 최종 버전은 **Dense 유사도만** 쓰는 함수였다. BM25 호출은 코드에 남겨 두고 꺼 뒀고, 배치는 Sparse 벡터를 계속 만들어 두었다.

|운영 함수에서 바뀐 것|효과|
|---|---|
|Sparse 항 제거|질의마다 BM25 인코딩을 하지 않아 처리 단계가 하나 줄었다|
|후보군 사번 목록을 인자로 받음|SQL 필터를 통과한 사람 안에서만 유사도를 계산한다. 계산량도 줄고, 조건 밖의 사람이 섞일 일이 없다|
|하한선 0.7 → 0.75, 상한 20 → 300명|유사도는 더 엄격하게 거르고, 결과 수는 넉넉하게 돌려준다|

돌아보면 하이브리드가 가장 필요했던 건 정형 조건과 정성 조건이 한 문장에 섞여 들어오던 초기 구조였다. 질의를 갈래로 나누고 정형 조건을 SQL로 빼낸 뒤에는, 경험 검색에 남는 게 주로 의미 비교였다. 다만 Dense만으로 충분한지 평가셋으로 비교해 확인하지는 못했다(7절). Sparse 벡터는 계속 만들어 두었기 때문에, 키워드 매칭이 다시 필요해지면 함수만 바꿔 되살릴 수 있다.

### 3.7 결과 화면

결과 화면에는 순위와 유사도(%)만이 아니라 직급·직무, **근거 문장**, 인재 유형 태그를 함께 보여 줬다. 왜 이 사람이 나왔는지 사용자가 직접 확인할 수 있게 하려는 것이었다. 결과가 600명을 넘으면 명단 대신 인원수만 돌려주고 조건을 좁히도록 했다. 너무 넓은 질의에 수백 명의 근거 문장을 만드는 비용을 쓰지 않기 위해서다.

## 4. 질의 전처리: LLM에게 맡긴 일과 맡기지 않은 일

질의 하나가 LLM 단계 다섯 개를 거친다(근거 문장 생성은 후보 문서마다 한 번씩). 모두 few-shot 예시를 붙인 GPT-4o-mini이고, 이 중 두 개(분류, Text2SQL)는 예시만으로 흔들려서 파인튜닝한 모델을 썼다. 초기 PoC는 GPT-3.5 few-shot으로 시작했다.

|단계|입력 → 출력|모델|
|---|---|---|
|4.1 갈래 분류|질의 → `{filter, job_history, experience}`|파인튜닝 4o-mini|
|4.2 Text2SQL|filter 문장 → `WHERE` 절|파인튜닝 4o-mini|
|4.3 이력 조건 추출|job_history 문장 → `{keyword, lower_bound, upper_bound}`|4o-mini few-shot|
|4.4 경험 키워드 추출|experience 문장 → 키워드 + 성공경험 여부|4o-mini few-shot|
|4.5 근거 문장 생성|질의 + 문서 → 근거 문장|4o-mini few-shot|

### 4.1 갈래 분류: "있는"과 "있었던"을 가르기

가장 어려운 건 같은 단어가 시제에 따라 다른 갈래가 되는 경우였다. "재무팀에 **있는**"은 현재 소속이라 필터고, "재무팀에 **근무했던**"은 과거 이력이라 직무이력이다. 프롬프트에 규칙을 명시하고, 헷갈리는 예시를 모아 파인튜닝했다.

|표현|갈래|규칙|
|---|---|---|
|"~에 있는", "~소속", "~근무하는"|filter|현재 상태|
|"~근무했던", "~경력 있는", "N년 일한"|job_history|과거 이력. 기간 표현도 여기로|
|"~가능한", "~능숙한", "~경험"|experience|서술 텍스트에서 찾을 역량|
|"A 아니면 B"|filter|문장을 고치지 않고 그대로 넘김. 해석은 Text2SQL이 함|

분류 단계에서 원문을 **고쳐 쓰지 말고 잘라서 그대로** 넘기게 한 것도 중요했다. 분류 모델이 "과장 이상"을 "과장급"으로 바꿔 쓰면 다음 단계가 다른 조건으로 해석했다.

### 4.2 Text2SQL: 생성된 SQL은 그대로 믿지 않는다

필터 갈래는 프로필 뷰의 스키마(컬럼 이름과 한국어 설명)를 프롬프트에 넣고 `WHERE` 절만 생성하게 했다. API는 고정 조건 뒤에 생성된 절을 붙여 실행한다.

```python
clause = text2sql("마케팅팀에 있는 과장 이상, 근속 5년 이상")
# → "org_name LIKE '%마케팅%' AND grade_rank >= 4 AND total_years >= 5"

sql = f"""
    SELECT empno FROM profile_filter_view
    WHERE 1=1
      AND <검색 대상 범위 고정 조건>
      AND {clause}
"""
```

운영하며 만난 문제는 거의 다 이 한 줄에서 나왔다.

|증상|원인|해결|
|---|---|---|
|`>=3and_<=4` 같은 문법 오류|모델이 연산자 주변 공백을 빼먹음|정규식 후처리로 공백·`AND` 보정|
|소속명 대소문자가 다르면 0명|영문이 섞인 조직명에 `LIKE` 사용|소속 컬럼은 후처리로 `ILIKE`로 교체|
|"직위"와 "직책"을 섞어 씀|둘 다 직급처럼 들림|스키마 설명과 예시를 보강하고 재학습|
|**고정 조건 밖의 사람이 결과에 섞임**|여러 소속을 `OR`로 나열할 때 괄호를 빼먹음. `AND 고정조건 AND A OR B`는 `(... AND A) OR B`로 해석돼, B에 해당하면 고정 조건을 건너뜀|자주 나오는 `OR` 묶음에 괄호를 씌우는 후처리 추가|

마지막 문제는 결과가 틀려도 에러가 나지 않아서 늦게 찾았다. 지금이라면 생성된 절 전체를 항상 `AND (...)`로 감싸고, 읽기 전용 계정으로 실행하고, 허용된 컬럼만 쓰였는지 검사한 뒤 실행하겠다.

### 4.3 이력 조건: 기간을 숫자로

직무이력 갈래는 LLM이 키워드와 기간 범위만 뽑고, 실제 조회는 DB 함수가 한다.

|입력|keyword|lower_bound|upper_bound|
|---|---|---|---|
|"재무에서 3-5년 경력있는"|재무|3|5|
|"웹 디자인 3년 이상"|웹 디자인|3|(없음)|
|"인사 4년 근무한"|인사|4|4|
|"재무 4년차인"|재무|3|4|
|"데이터 직무에서 일한"|데이터|0|(없음)|

"N년차"는 N−1년 이상 N년 이하로 해석하도록 규칙을 따로 줬다. 이런 규칙은 LLM이 알아서 맞히길 기대하기보다 프롬프트에 정의해 두는 편이 결과가 안정적이었다.

### 4.4 경험 키워드와 성공경험 플래그

경험 갈래는 문장을 그대로 임베딩하지 않고, 핵심 키워드만 남긴 뒤 임베딩했다. "인사 재배치 성공 경험 있는 사람 추천"은 `인사 재배치 |성공경험`이 된다. "있는 사람 추천" 같은 군더더기가 벡터를 흐리지 않게 하고, "성공"이 들어가면 플래그를 세워 성공 사례로 분류된 문서만 검색했다.

### 4.5 근거 문장 생성: 문서마다 병렬로

유사도 검색이 돌려주는 건 평가 문서 전체다. 사용자가 긴 문서를 읽지 않도록, 문서마다 "질의와 관련된 문장"을 LLM으로 뽑아 근거로 보여 줬다. 후보가 수십~수백 명이라 순차 호출로는 응답이 너무 느려서, 100건씩 묶어 비동기로 동시에 호출했다.

```python
async def evidence_for_all(query, documents, batch_size=100):
    results = []
    for i in range(0, len(documents), batch_size):
        batch = documents[i:i + batch_size]
        results += await asyncio.gather(*[
            chain.ainvoke({"question": f"[질의] {query}\n[문서] {doc}"}) for doc in batch
        ])
    return results
```

근거를 찾지 못한 문서는 빈 문자열을 돌려받아 결과에서 뺐다. 유사도는 넘었지만 실제로는 관련 문장이 없는 문서를 한 번 더 거르는 효과가 있었다.

### 4.6 데이터에 미리 붙여 둔 유형 태그

질의 시점의 처리와 별개로, 배치에서 평가 텍스트를 LLM으로 미리 정한 11가지 인재 유형(예: 전략형)으로 분류해 태그를 붙여 뒀다([1편](/spark/spark-etl-emr-serverless/) 4.4). 시연에서 "전략적인 사람"을 검색했을 때 상위 결과에 전략형 태그가 붙은 사람들이 나오는 것으로 검색 결과와 태그가 서로를 뒷받침하는지 확인했다.

## 5. 저장소 선택

### 5.1 Pinecone vs pgvector

PoC에서 같은 데이터를 두 곳에 넣고, 질의 결과를 나란히 보는 비교용 대시보드를 만들어 확인했다.

|기준|Pinecone|pgvector|
|---|---|---|
|정형 필터와 결합|메타데이터 필터는 되지만 복잡한 조인은 앱에서 처리|**SQL로 필터·조인·유사도를 한 번에**|
|기존 인프라|별도 SaaS, 데이터가 외부로 나감|이미 쓰는 PostgreSQL에 확장만 추가|
|민감 데이터|외부 저장이 부담|사내 관리 영역 안에 둠|
|대규모 성능|강점|수천 건 규모에서는 충분|

수천 건 규모, 정형 필터 중심, 민감 데이터라는 조건에서 pgvector를 택했다. 데이터가 수백만 건으로 커지면 전용 벡터 DB(Milvus 등)를 다시 검토하기로 했다.

### 5.2 RDS 버전과 구성

|결정|선택지|판단|
|---|---|---|
|엔진 버전|16.1 (안정 버전, pgvector 0.5) vs **16.3 (pgvector 0.7)**|0.7에서 `sparsevec`, `halfvec`이 추가됐다. Sparse 벡터를 전용 타입으로 다룰 여지를 두려고 버전 안정성보다 기능을 택했다. 실제 저장은 배치가 만든 `jsonb` 그대로 썼다(3.5)|
|가용성|Multi-AZ vs **Single-AZ**|Multi-AZ는 비용이 약 두 배. 원천 데이터가 따로 보관돼 있어 배치로 재구축할 수 있고, 실시간 핵심 서비스가 아니어서 Single-AZ로 충분하다고 판단|

### 5.3 성능 병목

질의가 몰릴 때 응답이 느려졌다. `ivfflat` 인덱스를 추가하고 인스턴스 사양을 조정해 개선했다.

```sql
CREATE INDEX ON profile_doc USING ivfflat (dense_vec vector_cosine_ops) WITH (lists = 100);
```

정형 필터로 후보를 먼저 줄인 다음 유사도를 계산하는 쿼리 구조도 계산 대상 자체를 작게 유지하는 데 도움이 됐다.

## 8. 실무 체크리스트

- [ ] 정형 조건(부서, 직급)은 벡터가 아니라 `WHERE` 필터로 처리하고 있는가.
- [ ] 필터를 유사도 계산보다 먼저 걸고 있는가.
- [ ] 한국어 BM25에 형태소 분석을 거친 토큰을 넣고 있는가.
- [ ] Dense와 Sparse의 가중치를 사례 기반 평가셋으로 비교했는가.
- [ ] LLM이 만든 SQL 절을 괄호로 감싸고, 허용 컬럼만 쓰였는지 검사한 뒤 실행하는가.
- [ ] 현재 상태와 과거 이력처럼 시제로 갈리는 조건을 분류 규칙에 명시했는가.
- [ ] 한 사람의 여러 문서가 결과를 도배하지 않게 사람 단위로 묶는가.
- [ ] pgvector 버전이 필요한 벡터 타입(`sparsevec`, `halfvec`)을 지원하는가.
- [ ] 결과에 점수만이 아니라 근거 텍스트를 함께 보여 주는가.

## 9. 정리

- **질의를 갈래로 나눴다.** 현재 상태는 Text2SQL, 과거 이력은 기간 조건, 역량은 벡터 검색으로 보내고 결과를 교집합으로 합쳤다.
- **필터는 SQL로, 뉘앙스는 벡터로.** 정형 조건까지 벡터에 맡기지 않은 것이 정확도와 속도를 함께 잡았다.
- **하이브리드로 시작해 Dense로 좁혔다.** Dense와 BM25를 섞는 함수를 만들어 튜닝했고, 정형 조건을 SQL로 빼낸 뒤 운영은 Dense로 단순화했다.
- **LLM 출력은 그대로 실행하지 않았다.** 생성된 SQL의 괄호 하나가 조회 범위를 바꿀 수 있었다.
- **도구는 규모와 데이터 성격에 맞췄다.** 수천 건, 민감 데이터, 필터 중심이라는 조건에서 pgvector를 택했다.
- **검색 품질의 상한은 데이터가 정한다.** 평가 텍스트에 없는 역량은 어떤 임베딩으로도 찾을 수 없다.

[1편](/spark/spark-etl-emr-serverless/)이 데이터를 모으는 일이었다면, 이 글은 그 데이터에서 조건에 맞는 사람을 찾는 일이었다.
